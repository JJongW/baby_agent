# 레포 규칙 — 브랜치, 커밋, PR, 머지

6명이 같은 레포를 다루므로 아래만 지키면 서로 안 꼬인다.

## 1. 내 폴더만 고친다
| 내 것 | 공통 (고치기 전에 단톡이나 이슈로 먼저 알린다) |
| --- | --- |
| `.claude/agents/<나>/` | `README.md`, `CLAUDE.md` |
| `.claude/skills/<나>-*/` | `docs/`, `scripts/`, `.github/` |
| `members/<나>/` | 다른 사람 폴더 전부 |

다른 사람 에이전트를 고치고 싶으면 직접 고치지 말고 이슈를 열어 주인에게 맡긴다.

## 2. 이슈 하나 = 브랜치 하나 = PR 하나
- 작업 전에 GitHub 이슈를 만든다. 제목은 무엇을 할지 한 줄
- 브랜치: `<나>/<종류>-<주제>` (예: `shin/feat-prd-reviewer`, `kwon/fix-figma-tokens`)
- 종류: `feat` 새 에이전트, `fix` 고침, `docs` 문서만, `chore` 설정
- 한 PR에 에이전트 하나가 기본. 여러 개를 한꺼번에 올리지 않는다

## 3. 커밋
- 형식: `<종류>(<나>): 무엇을 했나` (예: `feat(noh): API 리뷰 에이전트 추가`)
- 한국어로 쓴다

## 4. PR
- 제목은 커밋과 같은 형식. 본문은 PR 양식(`.github/pull_request_template.md`)을 채운다
- 올리기 전에 `bash scripts/check.sh`를 돌리고, 통과 결과를 PR 본문에 적는다. 리뷰어도 받아서 한 번 돌려 본다. 실패하면 머지하지 않는다
- 에이전트를 추가하거나 동작을 바꾸면 소개 카드도 같은 PR에 넣는다

## 5. 리뷰와 머지
- 리뷰어 1명 이상 승인 후 머지한다. 리뷰어는 같은 직군 1명을 먼저 고르고, 없으면 아무나
- 리뷰에서 보는 것: 이름 규칙, 소개 카드의 "왜"와 "근거"가 있는지, 비밀 값이 없는지, 남의 폴더를 건드리지 않았는지
- 머지는 **Squash and merge**만 쓴다. 머지는 PR을 올린 사람이 한다
- 머지 후 브랜치는 지운다
- `main`에 바로 push하지 않는다. force push 하지 않는다

## 6. 받은 다음
- 다른 사람 PR이 머지되면 `git pull`만 받으면 된다. 따로 설치할 것은 없다
- 에이전트가 안 보이면 Claude Code를 다시 열고 `/agents`로 확인한다

## 7. 넣지 않는 것
- API 키, 토큰, 비밀번호
- 회사 내부 자료, 고객 데이터, 개인 정보
- 내 컴퓨터에만 있는 경로 (예: `/Users/내이름/...`)
