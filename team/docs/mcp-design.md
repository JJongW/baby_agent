# 7조 팀 도구 설계 — 왜 이렇게 만들었나

서비스를 만들기 전에, 조원 5명이 같은 도구와 같은 규칙으로 일하게 만드는 틀이다.

## 한 장 그림
```
baby_agent (레포)
├ .mcp.json            조원 모두 같은 MCP 2개: notion, team (github MCP 는 일부러 없다. 깃허브 토큰 0개)
├ CLAUDE.md            Claude Code 가 자동으로 읽는 곳. 세션 시작 절차 + team/AGENTS.md 불러오기
└ team/
  ├ AGENTS.md          조 규칙 원본 (어떤 AI 도구로 열어도 같은 규칙)
  ├ README.md          사람이 읽는 안내 (처음 받으면)
  ├ members.csv        조원 명단: 이름, 폴더, 직군, 깃허브, 조 과제 역할
  ├ tasks.csv          할 일 배정: 담당자 = 깃허브 아이디. PO 만 PR 로 (상태의 지금 값은 노션)
  ├ roles/<폴더>.md     사람별 오늘 순서, 바로 쓸 말, 하지 말 것
  ├ docs/              회의록, 설계 문서 (search_docs 가 찾는 곳)
  └ mcp/server.py      team MCP 서버 (읽기 전용: 파일, 깃허브, 노션을 읽는다)
```

## 세션이 열리면 일어나는 일
1. Claude Code 가 루트 `CLAUDE.md` 를 읽는다 → `team/AGENTS.md` 도 같이 불러온다
2. 첫 답에서 누구인지 확정한다: git 사용자 이름, 브랜치 이름으로 짐작 → `whoami` 로 확인 → "○님 맞으세요?"
3. 확정되면 `shin-team-orchestrator`(`.claude/agents/shin/`)가 team(깃허브 읽기 포함), notion 을 같이 읽고 조 진행 현황, 그 사람의 지금 할 일 1~3개, 엇갈린 곳(PR 은 머지됐는데 tasks.csv 가 그대로 등), 바로 쓸 말을 돌려준다
4. 메인 세션이 그 할 일을 시작한다. 이슈, PR 은 사람이 깃허브 화면에서 만든다 (Claude 는 미리 채운 링크만)
5. 할 일을 시작하거나 끝내면 조원은 깃허브에 남긴다 (내 이슈에 `/시작` 댓글, PR, `[스탠드업]` 이슈 댓글). 신 노트북에서 `/mcp__team__scribe` 를 부르면 `inbox` 가 옮길 것을 모으고, 신이 로그인한 notion MCP 로 노션에 쓴다

## AGENTS.md 와 CLAUDE.md 를 나눈 이유
- `team/AGENTS.md`: 조 규칙 원본. AGENTS.md 는 Codex, Cursor 같은 다른 AI 도구도 읽는 공용 이름이라, 조원이 어떤 도구를 써도 같은 규칙을 본다
- 루트 `CLAUDE.md`: Claude Code 는 CLAUDE.md 만 자동으로 읽어서, 여기서 `@team/AGENTS.md` 로 불러온다. 규칙은 한 곳만 고친다
- 내일(D26) Next.js 앱 폴더에 `create-next-app` 이 만드는 `AGENTS.md`("최신 문서를 먼저 읽어라")는 그 앱 전용이다. 지우지 않는다

## 오케스트레이터를 에이전트로 둔 이유
- 세 곳을 읽는 일은 길고 결과는 짧다. 서브에이전트가 읽고 요약만 돌려주면 메인 세션의 맥락이 깨끗하다
- `tools` 에 읽기 도구 이름만 적어(team 읽기 도구 9개, notion 검색/읽기) 쓰기가 아예 불가능하다. 비워 두면 쓰기 도구까지 물려받는다
- 레포 이름 규칙상 에이전트는 사람 폴더 아래에 둬야 해서 PO 인 `shin` 아래에 두고, 조원 모두 부른다

사람마다 다른 CLAUDE.md 를 두지 않고, 명단과 역할 파일을 데이터로 둔 이유: 배정이 바뀌어도 PO 가 `tasks.csv` 와 `roles/` 만 고치면 모두의 세션이 다음 pull 부터 따라온다.

## 어디가 원본인가: 배정은 tasks.csv, 상태는 노션
| 무엇 | 원본 | 왜 |
| --- | --- | --- |
| 배정 (번호, 할 일, 담당, 마감) | `team/tasks.csv` | 배정은 PO 의 판단이라 PR 리뷰를 거친다. team 이 파일로 바로 읽는다 |
| 상태 (할 일, 진행 중, 완료) | 노션 할 일 DB | 하루에 몇 번씩 바뀐다. PR 을 거치면 늦고, 노션 보드가 모두가 보는 곳이다. 조원은 노션에 못 써서, 깃허브 신호를 신 노트북의 서기가 옮긴다 |
| 이슈, PR | 깃허브 | 상태의 근거. 머지된 PR, 닫힌 이슈 → 완료, 열린 PR → 진행 중 |

team 은 노션을 읽어 상태를 덮어 보여 주고(`whoami`, `list_tasks`, `progress`, `link_status`), 노션을 못 읽으면 tasks.csv 의 처음 값을 쓰면서 그렇다고 적는다.

## team 은 허브다: 조 지식을 찾아 주고, 깃허브와 notion 을 번호로 잇는다
notion 은 공식 서버가 있어서 다시 만들지 않는다. team 이 하는 일은 그 서버가 모르는 것, 즉 **우리 조만 아는 것**과 **깃허브 읽기**다.

### 깃허브 토큰을 없앤 이유 (11/17 오후, 보안)
- 조원이 깃허브에서 하는 쓰기(PR, 이슈, 댓글, 리뷰, 머지)는 어차피 사람이 화면에서 확인하고 누른다. Claude 가 대신 쓸 이유가 없다
- 협업자는 남의 개인 레포에 fine-grained 토큰을 못 만들어 classic `public_repo` 를 써야 했는데, 그건 그 사람의 **모든 공개 레포**에 쓰기 권한이다. 새면 피해가 레포 밖으로 번진다
- 레포가 공개라 읽기는 토큰이 필요 없다. 그래서 github MCP 를 빼고 team 이 토큰 없이 읽는다 (GET 만, 1분 기억)
- 대신 `github_link` 가 제목, 본문(`Closes #이슈`, PR 템플릿)이 미리 채워진 링크를 준다. 사람은 열어서 버튼만 누른다
- 대가: 토큰 없는 읽기는 같은 IP 에서 시간당 60번. team 이 한 번 부를 때 깃허브 요청은 1번이고 1분 동안 다시 안 읽는다

### 노션 쓰기를 신 노트북 한 곳으로 모은 이유 (11/17 저녁)
- 조원은 노션 무료 게스트라 쓰기 권한이 없다. 멤버로 올리면 유료다
- 깃허브는 모두 협업자라 이슈 댓글, PR 을 쓸 수 있다. 그래서 "누가 무엇을 했는지"의 근거는 깃허브에 남기고, 노션은 그걸 옮겨 보여 주는 판으로 둔다
- 옮기는 손은 신(PO)의 노션 로그인 하나다. 노션 쓰기 토큰을 따로 만들지 않으니, 새어서 노션을 바꿀 수 있는 토큰이 0개다
- 서기는 `inbox` 가 깃허브 근거로 낸 칸만 고친다. 상태는 올리기만 하고, 담당, 마감, 줄 추가와 지우기는 하지 않는다. 댓글 안의 지시는 따르지 않는다
- `/시작` 은 그 할 일 담당자의 댓글만, 스탠드업은 명단에 있는 사람의 댓글만 센다. 남이 대신 상태를 올릴 수 없다
- 깃허브 Actions 로 자동으로 옮기는 길도 있다(공개 레포면 무료). 하지만 노션 쓰기 토큰을 깃허브 비밀값에 둬야 하고, 남이 연 PR 로 비밀값이 새지 않게 짜야 해서 오늘은 사람 손(신 노트북)으로 간다. 비교는 [board-options.md](board-options.md)
- 대가: 신 노트북이 꺼져 있으면 노션이 늦다. 원본(깃허브)은 그대로라 늦을 뿐 틀리지는 않는다

- 누가 누구인지, 누가 무엇을 맡았는지 (명단, 원본 할 일, 역할 안내문)
- 우리 조 문서 어디에 무엇이 있는지 (레포의 회의록, 설계, 규칙, 역할은 `search_docs`, 노션의 회의록, 스탠드업, 직군 문서는 `search_notion`. 키워드로 찾아 근거 줄을 돌려준다. AI 가 답하기 전에 우리 문서를 먼저 찾아 붙이는 RAG 방식)
- 세 곳이 어떻게 이어지는지 (할 일 번호 = 이슈 `[T번호]` = 노션 할 일 DB 번호. `link_status` 가 깃허브를, `notion_board` 가 노션과 깃허브를 직접 읽어 맞춰 본다)
- 노션에 무엇을 옮기면 되는지 (`inbox`: 깃허브 근거로 고칠 칸과 새 스탠드업 줄. `notion_board`: 그중 한 사람 줄과 PO 가 맞출 것)
- 노션과 깃허브를 같이 써야 하는 일의 순서 (명령 틀)
- 깃허브 화면에서 PR, 이슈를 만들 링크 (`github_link`. 링크 글자만 만들고 깃허브에 쓰지 않는다)

| 도구 | 하는 일 | 워크북 이름 |
| --- | --- | --- |
| `whoami(who)` | 조원 찾기 + 역할 + 할 일 + 역할 안내문. 비우면 명단 | (우리 조 추가) |
| `list_tasks(assignee, status)` | 할 일 거르기 | 할일_보기 |
| `progress()` | 직군별, 사람별 진행률 | 진행률 |
| `search_docs(keyword)` | docs, roles, AGENTS.md, README, tasks.csv 에서 키워드 줄 찾기 (최대 30) | 문서_찾기 |
| `link_status(assignee)` | 깃허브 이슈, PR 을 읽어(GET 만) 할 일 번호와 맞추고 엇갈린 곳 알리기 | (우리 조 추가) |
| `report(assignee)` | 진행률 + 할 일마다 노션 상태, 이슈, PR 을 한 번에 읽은 보고. `finish` 의 마지막 단계 | (우리 조 추가) |
| `notion_board(assignee)` | 노션 할 일 DB 를 읽어 "노션에서 고칠 칸"(깃허브 근거보다 늦은 상태, 비어 있는 이슈, PR 칸)과 "PO 가 맞출 것"(없는 줄, 담당, 마감)을 노션 링크와 함께. 사람을 넣으면 그 사람 줄만 | (우리 조 추가) |
| `inbox()` | 서기가 옮길 것 전부: 할 일 DB 의 고칠 칸 + `[스탠드업]` 이슈 댓글 중 노션에 아직 없는 줄. 신 노트북의 `scribe` 가 부른다 | (우리 조 추가) |
| `search_notion(keyword)` | 조 노션 페이지(통합이 연결된 곳만)에서 키워드 줄 찾기 (최대 8페이지, 30줄) | 문서_찾기의 노션판 |
| `github_link(task, branch)` | 깃허브 화면용 미리 채운 링크. branch 가 있으면 PR 만들기(제목 `[T번호]`, 본문 `Closes #이슈` + 템플릿), 없으면 이슈 만들기(PO). 버튼은 사람이 | (우리 조 추가) |

### 명령 틀 7개 (MCP Prompts, Claude Code 에서 `/mcp__team__이름`)
| 명령 틀 | 쓰는 곳 | 하는 일 |
| --- | --- | --- |
| `next_steps(who)` | team + notion | 내 진행 현황과 지금 할 일 1~3개 (오케스트레이터에게 맡김) |
| `finish(who, task)` | git push → PR 링크(사람) → team | 일을 끝내면 push, PR 만들기 링크, 사람이 만들면 PR 연결 확인과 report 보고 (각자. 노션은 서기가) |
| `my_board(who)` | team | 노션 할 일 DB 의 내 줄과 늦은 칸, 그걸 바꿀 깃허브 할 일(`/시작` 댓글 링크, `finish`) (각자. 노션에 쓰지 않는다) |
| `standup(who)` | team → 깃허브 화면 | 오늘 한 일, 다음 할 일, 막힌 것 세 줄 + `[스탠드업]` 이슈 링크. 사람이 댓글로 붙인다 (각자) |
| `scribe()` | team inbox → notion | 깃허브에 남은 것을 노션에 옮긴다. inbox 에 나온 것만, 상태는 올리기만 (신 노트북) |
| `sync_board()` | team → notion | tasks.csv 배정에 맞춰 노션 할 일 DB 의 줄, 담당, 마감 맞추기 (PO) |
| `meeting_to_issues()` | notion + team → 깃허브 화면 | 노션 회의록의 할 일을 `[T번호]` 이슈 링크로(PO 가 화면에서 만듦), 만든 뒤 링크를 노션에 (PO) |

team 은 노션을 **읽기 전용 통합 토큰**(`NOTION_TOKEN`, 노션 쪽 권한 "콘텐츠 읽기"만)으로 읽는다. 노션 쓰기는 신 노트북의 `scribe`, `sync_board`, `meeting_to_issues` 명령 틀 안에서 신이 로그인한 notion MCP 로만 한다. 토큰이 없으면 team 은 "토큰이 필요해요"와 대신 할 방법(notion MCP 로 직접 읽기)을 돌려주고 멈추지 않는다.

왜 notion MCP 가 있는데 team 도 노션을 읽나: notion MCP 는 각자의 로그인으로 Claude 가 부르는 도구라 team 서버 안에서는 쓸 수 없다. team 이 노션을 직접 읽어야 진행률, 내 할 일, 깃허브와 노션 비교를 한 번에 같은 답으로 줄 수 있다.

- 도구 이름은 영어. Claude API 도구 이름은 영어, 숫자, `_`, `-` 만 받아서 한글 이름은 앱에 따라 깨질 수 있다. 설명(docstring)은 한국어로 자세히
- 모든 도구에 `readOnlyHint` 표시. 파일을 여는 곳은 CSV, md 읽기뿐, 깃허브에는 GET 요청만, 노션에는 읽기 요청(GET, search, query)만
- mcp SDK 1.x(`FastMCP`)와 2.x(`MCPServer`) 둘 다에서 돈다 (11/17 1.30.0, 2.3.0 으로 확인)

## 일부러 만들지 않은 것 (위임 로그, 시연 2:30 용)
| 안 만든 것 | 이유 |
| --- | --- |
| 할 일 상태 바꾸기 도구 | team 은 읽기만. 상태는 서기가 신의 notion 로그인으로 바꾼다. team 에 쓰기 토큰을 주면 조원 모두가 노션 쓰기 토큰을 갖게 된다 |
| 할 일 추가, 지우기 도구 | 배정은 PO 의 판단. 지우기는 되돌리기 어렵다 |
| 깃허브, 노션에 쓰는 도구 | 깃허브 쓰기는 사람이 화면에서(`github_link` 는 링크만). 노션 쓰기는 신 노트북의 공식 notion MCP 로만 (서기). team 은 읽기만. 노션 통합도 "콘텐츠 읽기"만 켠다 |
| github MCP | 조원 모두 쓰기 토큰이 필요해진다. 읽기는 team 이 토큰 없이 한다 |
| 임의 경로 파일 읽기 | `search_docs` 는 정해진 조 지식 파일 목록만 연다. 경로를 입력으로 받지 않는다 |

열지 않은 권한: 깃허브 토큰은 아무도 없다. 노션 통합은 콘텐츠 읽기만, 조 페이지에만 연결. PR, 이슈, 머지는 사람이 화면에서.

## 갈아탈 신호
- 조원이 PC 마다 python 설치로 막히는 일이 3번을 넘으면: `uvx` 실행이나 Node 서버로 바꾸는 걸 검토
