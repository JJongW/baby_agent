# yoon-pr-intent-check

- **만든 사람**: 윤
- **직군**: 개발
- **만든 날**: 2026-11-05

## 왜 만들었나

작업을 하다 보면 계속 수정해야 할 것들이 생긴다. 그러다 보면 PR에 처음 의도했던 것과 다른 변경이 계속 추가되면서 PR의 단위가 커진다. 하나하나는 작은 수정이라도 쌓이면 PR의 의도가 모호해진다.

하나의 PR에 원래 의도했던 목적의 변경만 담도록, PR을 올리기 전에 범위를 확인하려고 만들었다.

## 근거

PR이 커지고 의도가 흐려지면 이런 문제가 생긴다.

- **리뷰가 어려워진다**: 리뷰어가 목적인 변경과 곁다리 변경을 구분해야 하고, 변경이 많을수록 버그를 놓친다
- **되돌리기 어려워진다**: 일부만 되돌리고 싶어도 다른 변경과 묶여 있다. 특히 squash 머지를 쓰면 커밋 하나로 합쳐져서 더 그렇다
- **이력을 따라가기 어려워진다**: `git blame`으로 찾은 PR의 제목과 상관없는 변경이면 왜 바뀌었는지 알 수 없다
- **머지가 늦어진다**: 큰 PR은 리뷰가 오래 걸리고, 그 사이 다른 브랜치와 충돌이 생긴다

팀 규칙(`docs/rules.md` 2절)도 "이슈 하나 = 브랜치 하나 = PR 하나"를 기본으로 한다. 이 에이전트는 그 규칙을 PR 안의 변경 단위까지 지키도록 돕는다.

설계에서 정한 것:

- **의도를 모르는 채로 먼저 요약한다**: 사용자의 설명을 먼저 읽으면 그 관점으로만 diff를 읽게 된다. diff만 보고 요약한 뒤 의도와 비교해서, 둘이 크게 다르면 그것부터 알린다
- **의도의 출처를 고정하지 않는다**: 사람마다, 작업마다 이슈를 쓰기도 하고 문서를 쓰기도 한다. 설명, 이슈 번호, 문서 경로 중 무엇이든 받고, 없으면 브랜치 이름과 커밋에서 추론한다
- **작은 정리는 사용자가 정한다**: 의도한 코드를 고치면서 같이 손댄 이름 변경, 포맷 같은 정리는 무조건 빼라고 하면 귀찮아서 안 쓰게 되고, 그냥 두면 쌓인다. 그래서 따로 모아 보여 주고 판단은 사용자에게 맡긴다

## 어떻게 다루나

- **부르는 때**: PR을 올리기 전에, 브랜치에 의도 밖의 변경이 섞이지 않았는지 확인하고 싶을 때
- **부르는 말 예시**:
  - "yoon-pr-intent-check로 이 브랜치 봐줘. 의도는 로그인 실패 시 최대 3회 재시도"
  - "yoon-pr-intent-check로 점검해줘. 의도는 #42"
  - "yoon-pr-intent-check로 점검해줘. 의도는 docs/retry.md, 기준 브랜치는 develop"
  - `@agent-yoon-pr-intent-check 의도는 #42` (이렇게 부르면 이 에이전트가 꼭 실행된다)
- **넣는 것**: 의도(한 줄 설명, 이슈 번호, 문서 경로 중 하나). 기준 브랜치는 생략하면 최신으로 받은 `origin/<기본 브랜치>`를 쓴다. 의도를 생략하면 브랜치 이름과 커밋 메시지에서 추론하는데, 이때는 빠진 것을 확인하지 못한다
- **받는 것**: 판정 한 줄, 의도와 출처, 의도 없이 쓴 실제 변경 요약, 그리고 변경을 세 칸으로 나눈 목록
  - ✅ 의도 안: 의도를 구현하는 변경
  - 🤔 직접 정하기: 의도한 코드를 고치면서 같이 손댄 작은 정리. 둘지 뺄지는 사용자가 정한다
  - ✂️ 분리 추천: 의도와 관계없는 변경. 별도 PR로 빼기를 권한다
  - 마지막에 빠졌거나 확인하지 못한 것
- **쓰는 도구**: Read, Grep, Glob, Bash. Bash는 git 조회 명령, `git fetch`, `gh issue view`에만 쓴다. 파일을 고치지 않는다

## 한계와 주의

- Bash를 읽기 명령(`git diff`, `git log`, `gh issue view` 등)에만 쓰도록 하는 제한은 에이전트 본문의 지시문뿐이다. `tools` 설정으로는 명령 단위 제한을 걸 수 없어서, 다른 명령을 실행하지 못하게 막는 장치는 없다
- 버그, 성능, 코드 스타일은 보지 않는다. 코드 리뷰는 다른 도구로 한다
- 칸 나누기는 에이전트의 판단이다. 특히 ✂️ 분리 추천은 사람이 확인하고 정한다
- 의도가 구체적일수록 결과가 정확하다. "로그인 개선"보다 "로그인 실패 시 최대 3회 재시도"처럼 확인할 수 있는 조건을 주면 빠진 것까지 찾는다
- 이슈 번호로 부르려면 `gh` CLI가 설치되어 있고 로그인되어 있어야 한다. 이슈를 읽지 못하면 다음 출처로 넘어가고 결과에 그 사실을 적는다
