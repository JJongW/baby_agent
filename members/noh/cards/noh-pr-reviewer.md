# noh-pr-reviewer

- **만든 사람**: 노
- **직군**: 개발
- **만든 날**: 2026-11-05

## 왜 만들었나
머지하다가 충돌이 난 적이 있다. 충돌은 머지 버튼을 누르는 순간에야 알게 되는 경우가 많아서, 그때부터 원인을 찾고 푸느라 시간이 들었다. 이런 오류를 머지 전에 미리 잡아 줄 도구가 필요하다고 생각했다.

또 이 레포는 PR마다 리뷰어 1명이 승인해야 머지된다. 리뷰어가 diff를 처음부터 손으로 읽으면 시간이 걸리고, 바뀐 함수를 부르는 다른 곳, 예외 처리, 섞여 들어간 비밀 값처럼 놓치기 쉬운 것을 빠뜨린다. 리뷰 전에 이 에이전트로 한 번 훑어서 사람은 판단에 집중하려고 만들었다.

## 근거
- 직접 겪은 머지 충돌: 그래서 코드를 읽기 전에 `main`과 충돌이 나는지부터 확인하게 했다. `git merge-tree`로 작업 폴더를 건드리지 않고 충돌 파일을 미리 보고, 브랜치가 `main`보다 얼마나 뒤처졌는지도 알려 준다
- 5명이 한 레포에서 동시에 작업해서, 오래된 브랜치일수록 그사이 `main`이 바뀌어 충돌이 날 가능성이 커진다
- 팀 규칙 `docs/rules.md` 5절이 리뷰에서 보라고 한 것(이름 규칙, 소개 카드의 "왜"와 "근거", 비밀 값, 남의 폴더를 건드렸는지)을 체크 항목으로 그대로 넣었다
- 개발 PR에서 머지를 막아야 하는 문제(동작 오류, 보안, 데이터 손실)를 먼저 보고, 스타일 지적은 빼서 결과가 짧고 바로 쓸 수 있게 했다
- 코드를 고치지 않는 읽기 전용이라, 남의 PR에 써도 파일이 바뀔 걱정이 없다

## 어떻게 다루나
- **부르는 때**: PR을 올리기 직전 내 변경을 점검할 때, 다른 사람 PR 리뷰를 맡았을 때
- **부르는 말 예시**: "noh-pr-reviewer로 PR #5 리뷰해줘", "noh-pr-reviewer로 지금 브랜치 봐줘"
- **넣는 것**: PR 번호, 브랜치 이름. 아무것도 안 주면 지금 브랜치와 `main`의 차이
- **받는 것**: 맨 먼저 `main`과 충돌이 나는지(충돌 파일, 뒤처진 커밋 수, 해결 방법). 그다음 문제마다 심각도(막음 / 고침 권장 / 확인 필요), 위치(`파일:줄`), 무엇이 문제인지, 고치는 방향. 맨 끝에 머지 가능 여부 한 줄
- **쓰는 도구**: Read, Grep, Glob, Bash. Bash는 `git diff`, `gh pr diff` 같은 읽기 명령에만 쓴다. 파일을 고치지 않는다

## 한계와 주의
- 충돌을 알려 주기만 하고 직접 풀지 않는다. 충돌을 풀고 나면 다시 불러서 확인한다
- `git merge-tree --write-tree`는 git 2.38 이상에서 된다. 그보다 낮으면 PR 번호로 불러서 GitHub의 충돌 표시를 본다
- 테스트를 직접 돌리지 않는다. 돌려 볼 명령을 알려 줄 뿐이다
- PR 번호로 부르려면 `gh` CLI가 설치되어 있고 로그인되어 있어야 한다
- 업무 맥락(기획 의도, 디자인 결정)은 모른다. "확인 필요"로 나온 항목은 작성자에게 직접 묻는다
- 에이전트가 승인해도 사람 리뷰어의 승인을 대신하지 않는다
