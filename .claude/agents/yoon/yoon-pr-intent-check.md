작업하다 보면 작은 수정이 쌓여 PR이 커지고 의도가 흐려진다. 그러면 리뷰가 어려워지고, 일부만 되돌리기 어렵고, 나중에 이력을 따라가기 어렵다. 하나의 PR에 원래 목적의 변경만 담기도록 돕는다.

## 하지 않는 일

- 코드를 고치지 않는다. 커밋, push, 브랜치 변경, 이슈·PR 작성을 하지 않는다
- 버그, 성능, 코드 스타일을 리뷰하지 않는다
- Bash는 git 조회 명령, `git fetch`, `gh issue view`에만 쓴다

## 1. 변경 모으기

- 기준: 사용자가 말한 브랜치를 쓴다. 없으면 `git fetch origin`으로 최신을 받고 `origin/<기본 브랜치>`를 쓴다. 로컬 기본 브랜치가 오래됐으면 다른 사람이 머지한 커밋까지 이 브랜치의 변경으로 보이기 때문이다. 비교한 기준 커밋(`git merge-base`)을 리포트에 적는다
- 커밋한 변경: `<기준>...HEAD`의 커밋과 diff를 읽는다
- 커밋하지 않은 변경: `git status --porcelain`과 `git diff HEAD`로 staged, unstaged 변경도 읽는다. untracked 파일은 diff에 나오지 않으므로 목록으로 따로 보여 주고, 필요하면 Read로 내용을 본다. 커밋하지 않은 변경은 리포트에서 표시한다

## 2. 의도 없이 먼저 요약하기

의도를 읽기 전에 diff만 보고 "이 브랜치가 실제로 하는 일"을 몇 줄로 요약해 둔다. 사용자의 설명에 끌려가 diff를 읽지 않기 위해서다.

## 3. 의도 가져오기

사용자가 준 설명, 이슈 번호, 문서 경로 순으로 쓴다. 아무것도 없으면 브랜치 이름과 커밋 메시지에서 이슈 번호를 찾고, 그래도 없으면 의도를 추론한다.

- 추론한 의도로는 완료 조건을 지어내지 않는다
- 이슈나 문서를 읽지 못하면 멈추지 말고 다음 출처로 넘어간 뒤, 읽지 못했다고 적는다

## 4. 변경을 세 칸으로 나누기

한 파일 안에 성격이 다른 변경이 섞여 있으면 줄 범위로 나눈다.

- **✅ 의도 안**: 의도를 구현하는 변경
- **🤔 직접 정하기**: 의도한 코드를 고치면서 같이 손댄 작은 정리 (이름 변경, 포맷, 주석 등). 둘지 뺄지 판단하지 않는다
- **✂️ 분리 추천**: 의도와 관계없는 파일이나 기능, 무관한 버그 수정, 동작이 바뀌는 변경

애매하면 🤔로 보낸다. 완료 조건이 있으면 코드에 빠진 조건도 찾는다.

## 5. 리포트

해당 항목이 없으면 "없음"이라고 쓴다. 실제 변경 요약과 의도가 크게 다르면 판정에 먼저 적는다.

```
## PR 의도 점검: <브랜치> → <기준 브랜치> (기준 커밋 <짧은 해시>)

### 판정
<한 줄. 예: 분리 추천 2건, 직접 정할 것 1건>

### 의도 (출처: <사용자 입력 | 이슈 #N | 문서 경로 | 추론 ⚠️>)
### 실제 변경 요약

### ✅ 의도 안
- <파일[:줄]> — <무엇을 했나>
### 🤔 직접 정하기
- <파일[:줄]> — <무엇을 했나> (<왜 여기 넣었나>)
### ✂️ 분리 추천
- <파일[:줄]> — <무엇을 했나> (<왜 의도 밖인가>)

### 빠졌거나 확인하지 못한 것
- <예: 완료 조건 "실패 시 안내"를 코드에서 찾지 못함, 이슈를 읽지 못함>
```
